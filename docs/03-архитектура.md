# Pathway — стек и архитектура

## Стек

| Слой | Выбор | Почему |
|---|---|---|
| Платформа | **Expo** (React Native), TypeScript | Один код на iOS и Android |
| Навигация | **expo-router** | Файловая маршрутизация, экранов мало — хватит с запасом |
| База | **expo-sqlite** + **Drizzle ORM** | Записи это лог; нужны агрегаты, миграции и типы |
| Состояние | **Zustand** | Минимальный, без бойлерплейта. Redux тут — из пушки по воробьям |
| Анимации | **react-native-reanimated** | Идёт в Expo, работает в UI-потоке |
| Тактильный отклик | **expo-haptics** | |
| Шеринг | **react-native-view-shot** + **expo-sharing** | Рендерим карточку как компонент → PNG → системное меню |
| Шрифты | **expo-font**, Unbounded + Manrope | Кириллица, табличные цифры, открытая лицензия OFL |
| Звук | **expo-audio** | Звук победы, уважает беззвучный режим |
| Сборка | **Локально** | Android — Gradle на своей машине, iOS — Xcode на Mac. Облачных сервисов сборки нет |

### Чего в стеке нет и почему

**Нет бэкенда.** Нет сервера — нет расходов, нет утечек, нет политики о сборе данных, нет половины вопросов на ревью. Это сильная позиция, а не экономия.

**Нет аналитики в первой версии.** Любой SDK аналитики обязывает раскрывать сбор данных в App Privacy и Data Safety. Пока приложение не собирает вообще ничего, обе анкеты заполняются в одно нажатие «Нет».

**Нет MMKV вместо SQLite.** MMKV быстрее и проще, но записи — это растущий лог, по которому нужны суммы, группировки по дням и миграции при обновлениях. На key-value это выльется в ручную сериализацию и боль на первом же изменении формата.

## Модель данных

```sql
CREATE TABLE goals (
  id            TEXT PRIMARY KEY,
  title         TEXT    NOT NULL,           -- «Тысяча отжиманий»
  target        INTEGER NOT NULL,           -- 1000
  description   TEXT    NOT NULL,           -- «По 30–50 за подход», может быть пустым
  quick_steps   TEXT    NOT NULL,           -- JSON: [10, 30, 120]
  status        TEXT    NOT NULL,           -- 'active' | 'archived'
  created_at    INTEGER NOT NULL,
  completed_at  INTEGER
);

CREATE TABLE entries (
  id          TEXT    PRIMARY KEY,
  goal_id     TEXT    NOT NULL REFERENCES goals(id) ON DELETE CASCADE,
  day         TEXT    NOT NULL,             -- локальный день: «2026-07-17»
  amount      INTEGER NOT NULL,             -- всегда больше нуля
  created_at  INTEGER NOT NULL,
  updated_at  INTEGER NOT NULL             -- последний тап или правка этого дня
);

-- Одна запись на день у каждой цели
CREATE UNIQUE INDEX one_entry_per_day ON entries(goal_id, day);

-- База физически не даст завести вторую активную цель
CREATE UNIQUE INDEX one_active_goal ON goals(status) WHERE status = 'active';
```

### Три правила, которые нельзя нарушать

**1. Прогресс не хранится. Он вычисляется.**

Никакого поля `current` в `goals`. Прогресс — это всегда `SELECT SUM(amount) FROM entries WHERE goal_id = ?`. Единственный источник правды — лог записей.

Стоит завести кэшированное поле «для скорости» — и через месяц найдётся путь, на котором счётчик и история разошлись. Пользователь увидит «870» вверху и 88 записей по 10 внизу, и никогда больше не поверит приложению. Для трекера доверие к цифре — это весь продукт.

Записей физически не может быть много (несколько тысяч за годы), `SUM` по индексу мгновенен. В памяти агрегат держим в Zustand, но истина — в базе.

**2. Одна активная цель — инвариант базы, а не проверка в коде.**

Частичный уникальный индекс `one_active_goal` делает вторую активную цель невозможной на уровне SQLite. Проверка в UI обходится багом, гонкой или следующим разработчиком. Индекс не обходится ничем.

**3. Одна запись — один день, и записи всегда положительные.**

Времени у записей нет: человеку не важно, занимался он в 13:10 или 12:44. День как единица убирает окно склейки, группировку истории и делает правку прямой.

Отрицательных записей не бывает — сделать минус невозможно. Поэтому прогресс не может уйти в минус: не из-за проверки, а потому что нечему. Ошибку исправляют правкой дня, ноль убирает день целиком.

## Ключевой алгоритм: тап в день

**Как НЕ надо:** копить сумму в памяти и записать в базу по таймеру. Приложение убьют, телефон сядет, пользователь свернёт — и подходы пропадут. Потеря данных здесь недопустима: человек уверен, что засчитал.

**Как НЕ надо-2:** читать `amount` в JS, прибавлять шаг и писать сумму обратно. Три быстрых тапа читают одно значение и затирают друг друга — два подхода из трёх исчезают. Проверено параллельной записью: засчитывается 10 вместо 30.

**Как надо — UPSERT, складывает база:**

```sql
INSERT INTO entries (id, goal_id, day, amount, created_at, updated_at)
VALUES (?, ?, ?, ?, ?, ?)
ON CONFLICT (goal_id, day)
DO UPDATE SET amount = amount + excluded.amount, updated_at = ?;
```

Один запрос, атомарный. База сама решает, завести день или дописать в существующий, и сама складывает. Данные на диске после каждого тапа.

**Отмена** снимает всю сессию — всё, что натапано, пока горит плашка. Сессия живёт в памяти (`day` + `amount` каждого тапа); при откате раскладывается по дням, потому что долгая сессия может переехать через полночь.

**Правка дня:** `UPDATE entries SET amount = ? WHERE id = ?`. Ноль — `DELETE`.

## Архитектурные правила

Эти правила существуют, чтобы каждый следующий блок ложился в проект без переписывания предыдущего.

**1. Домен ничего не знает про React и про SQL.** Всё в `src/domain/` — чистые функции над обычными объектами. Их можно тестировать без эмулятора и без базы. «Достигнута ли цель», «сколько осталось», «какой сегодня день цели» — это домен, а не компонент.

**2. Ни одного цвета и отступа в коде компонента.** Только `tokens.ts`. Увидел `#2F86FF` или `padding: 24` в компоненте — это ошибка. Иначе смена акцента через полгода превращается в раскопки по сорока файлам.

**3. Экран не ходит в базу напрямую.** Экран → стор → репозиторий → база. Однонаправленно.

**4. Фичи изолированы.** `features/share` не знает про `features/celebration`. Общее живёт в `ui/components` или `domain`.

**5. Новый блок не правит домен предыдущего блока.** Если пришлось — значит, домен был спроектирован неверно, и это повод остановиться и обсудить, а не подпереть костылём.

## Тесты

Прицельно, без фанатизма. Покрываем то, где ошибка стоит дорого:

- `domain/progress.ts` — суммы, остаток, перевыполнение, деление на ноль, правка дня;
- `domain/day.ts` — границы дня, переход через полночь, сортировка ключей;
- `domain/undo.ts` — сессия отмены, раскладка по дням;
- инварианты базы — вторая активная цель и второй день должны падать.

UI-тесты не пишем: экранов мало, всё проверяется руками на живом телефоне за минуту.
